# MeetFlow 底层逻辑：给第一次接触项目的人

这份文档用来理解项目、准备汇报和回答追问。先读懂“为什么要这样做”，再去记技术名称。它与同目录的PPT、讲解稿配套：PPT是给观众看的提纲，讲解稿是上台时怎么说，这里解释提纲背后的原因。

阅读路线：时间紧先看第1、2、5、8、13节；完整读一遍，再试着回答最后的自测题。

## 1. 一句话讲清楚项目

MeetFlow（凑时）帮助课程小组收集大家的空闲时间，比较适合开会的时段，确认会议，并把讨论结果变成有负责人、有截止时间、能跟进的任务。

可以把它理解成一位做事有记录的小组协调员。他主要做四件事：问大家什么时候有空，整理答案，记录最终决定，跟进谁去完成什么。

软件没有替大家开会，也不会替执行人完成任务。它把原来散在聊天里的信息，变成规则明确、能够查回去的记录。

## 2. 为什么有群聊了，还需要这个系统？

假设四个人准备课程展示。群里依次出现：“我周三可以”“我晚上不行”“周四呢”“那就周三吧”。问题不是没人说话，而是信息难以比较：哪个时间谁有空、负责讲技术的人能不能到、谁还没回复，都要人工翻聊天记录。

开完会又出现第二个问题：“把接口说明补一下”。如果没有指定谁做、什么时候做完，几天后就容易没人跟进。

因此项目连接了两段事情：

```text
会前：收集时间 → 比较风险 → 确认会议
会后：记录决定 → 分配任务 → 人工更新进度
```

**项目的价值在这条连续流程。** 页面漂亮、按钮能点，只是让这条流程好用的手段。

按课程NABCD来讲：N是上述需求，A是三态填写和会议任务流程，B是预期减少汇总与跟进成本，C是群聊、问卷、共享日历等替代方式，D是先让课程小组试用的推广路径。这里的收益是待验证的目标，不能说已经证明节省了多少时间。

## 3. 系统里到底存了哪些东西？

把“小组、排期、会议、任务”分清楚，后面的逻辑就容易理解。

| 东西 | 通俗理解 | 例子 |
| --- | --- | --- |
| 用户 | 在系统里有身份的人 | 马若曦、陈明强 |
| 小组 | 一批共同协作的人 | 软件工程课程小组 |
| 排期 | 一次“大家什么时候能开会”的征询 | 为展示准备会收集三个时段 |
| 候选时段 | 排期提供的一个选项 | 11月8日11:00—11:30 |
| 参与者与答案 | 这次问了谁，每个人对每个时段怎么选 | 陈明强对第二时段选有空 |
| 会议 | 负责人已经确定下来的安排 | 最终选第二时段开会 |
| 任务 | 会议后需要落实的一件事 | 陈明强在截止前整理反馈 |

它们的关系是：一个小组可以多次排期；一次排期包含多个候选和参与者；确认后最多生成一场会议；一场会议可以有多项任务。议程和纪要保存在会议上，分别记录“准备谈什么”和“实际决定什么”。

为什么排期和会议分开？因为“正在问时间”和“已经决定时间”是两件事。没有这层区分，就很难判断大家能否继续修改答案，以及系统是否已经正式生成会议。

为什么任务要关联会议？以后看到“整理反馈”，可以查到它来自哪场讨论，而不只是一张没有背景的待办清单。

## 4. 谁能做什么，为什么要检查两遍？

小组角色主要是负责人和成员。“必到”是某次排期中的出席重要性，**不是管理员权限**。普通成员也可以被设为必到；某人重要，并不代表他能改别人的答案。

负责人管理排期、确认会议、编辑纪要和分配任务；参与者填写自己的时间。任务执行人可以更新自己的任务进度，其他普通成员不能替他随意修改。负责人也有任务管理权限，具体以操作规则为准。

界面会隐藏无权限的按钮，但这只能减少误操作。有人仍可能绕过页面，直接向系统发送请求，所以后端必须再检查：你是否登录、是不是这个小组的人、对这项操作有没有权限。

可以类比门禁：页面是门口指示牌，后端检查才是真正的刷卡验身份。只把按钮藏起来，不能算权限做完了。

## 5. 三态填写与“未填”有什么区别？

用户主动选择的是三态：有空、勉强、没空。系统另外保留“未填”，表示还没有得到答案。

| 状态 | 含义 | 应该怎样理解 |
| --- | --- | --- |
| 有空 | 可以参加 | 已明确同意这个时间 |
| 勉强 | 能协调，但不理想 | 比没空好，仍需沟通 |
| 没空 | 不能参加 | 已知冲突 |
| 未填 | 没有得到回答 | 出席情况未知 |

**未填不等于有空，也不等于没空。** 同学没回消息，你不能认为他答应了，也不能断言他一定来不了。

时间矩阵就是把“人 × 候选时段”的答案铺成一张表。看一列，知道这个时段哪些人能来；看一行，知道这个人对各个时段的选择。

发布后冻结候选时段和参与者，也是在保护答案含义。假设有人回答了“周三10点有空”，负责人随后把同一个选项改成周四，这条旧答案就不能继续算有效。第一版用冻结规则避免这种歧义。

## 6. 推荐时间到底怎么算？是不是AI猜的？

当前使用的是确定的规则评分与排序，没有调用大模型来猜大家什么时候有空。相同的参与者、候选和答案，会得到相同的排名；修改答案后重新计算，结果可能变化。

先分清两个问题：**分数怎么算**，以及**最后怎么排**。

### 6.1 先算每个时段的分数

普通成员权重是1，必到成员权重是3。每个人的选择先换成一个值：有空为2，勉强为1，没空为−2，未填为0。

```text
每人的基础贡献 = 出席权重 × 选择对应的值
基础分 = 所有人基础贡献相加
最终分 = 基础分 − 20 × 必到没空人数 − 2 × 全部未填人数
```

例如普通成员“有空”贡献2分，必到成员“有空”贡献6分。必到成员“没空”除了基础贡献为−6，还会带来额外的20分扣分。未填没有正向贡献，并且每人扣2分。

这些数字是当前项目的规则选择，表达“更重视关键成员、对未知保留谨慎”。它们不是经过用户实验得到的最优参数，也不是所有排期工具必须采用的标准。

### 6.2 再按优先级排列

从前往后依次比较：

1. 必到没空的人数，更少的优先。
2. 如果相同，最终得分更高的优先。
3. 如果还相同，有空人数更多的优先。
4. 再相同，开始时间更早、结束时间更早的优先。
5. 最后用候选的固定编号区分，保证顺序稳定。

这叫“逐级比较”。像考试排名先看总分，平分再看单科，不能把后面的条件拿来推翻前面的条件。这里把必到冲突放在最前面，所以没有必到冲突的时段，不会只因为另一个时段普通成员贡献高就排到其后。

### 6.3 用PPT里的例子算一次

下面是示意数据，两位必到、两位普通成员，不是真人调查。

| 参与者 | A | B | C |
| --- | --- | --- | --- |
| 负责人，必到 | 有空 | 有空 | 有空 |
| 另一位必到成员 | 没空 | 有空 | 未填 |
| 普通成员甲 | 有空 | 勉强 | 有空 |
| 普通成员乙 | 有空 | 有空 | 有空 |

- A：基础分为6−6+2+2＝4；一位必到没空，再扣20，最终 **−16**。
- B：基础分为6+6+1+2＝15；没有额外扣分，最终 **15**。
- C：基础分为6+0+2+2＝10；一位未填扣2，最终 **8**。

结果是 **B → C → A**。三个时段都有三个人选有空，但风险完全不同：A有必到冲突，C有关键成员的未知答案，B仍有一位普通成员勉强。因此推荐不应只显示一个“第一名”，还要显示理由和风险。

## 7. 第一名能不能直接当成最终决定？

不能。排名只回答“按当前规则，哪个相对更合适”，不保证所有人都能来。

如果所有时段都有人没空，系统仍然能排出第一名，但需要提示“排名不代表全员可参加”。必到未填要提示出席未确定，必到勉强要提示需要协调。

负责人结束收集后才确认会议。当前规则中，如果存在必到没空、必到未填，或者选择的不是排名第一的时段，需要明确确认风险并填写理由；必到勉强会提示协调。

系统允许人作最终判断，同时保留判断依据。例如某位必到成员后来线下确认能协调，负责人可以解释原因，而不是偷偷改掉那个人的答案。

## 8. 点“确认会议”后，为什么不只是新增一条记录？

正常流程看起来很简单：选时段，生成会议，把排期标为已确认。但真实操作会出现重复点击、网络延迟、两台浏览器同时操作、写入失败等情况。

设想系统先保存会议，再更新排期，中间突然失败：会议已经有了，排期却还显示没确认。下次再点，可能又生成一场。为了避免这种“做了一半”的状态，系统把相关修改放在同一个**事务**里。

事务可以理解为“一起成功，或一起撤回”的打包操作：

```text
收到确认请求
  → 取得数据库写锁
  → 再查身份、排期状态、候选是否属于本次排期
  → 基于当前数据重新检查推荐与风险
  → 写入会议，同时把排期改为已确认
  → 一起提交成功，才回复成功
```

写锁像办理同一项业务时先排队，避免互相冲撞；进入事务后还要重查，因为你打开页面时的状态，可能已经被另一个操作改变了。

数据库还规定“一个排期最多关联一场会议”，这是**唯一约束**，相当于最后一道硬性检查，防止程序某个分支漏了校验。

如果第一次其实保存成功，只是成功回复没有到达浏览器，再确认相同候选会返回原会议，而不是新建。这叫**幂等**：重复执行同一意图，业务结果不重复。确认以后再换一个候选则会发生冲突，不能悄悄生成第二场或覆盖原安排。

对应PPT顺序图：横向是浏览器、业务服务、数据库三个参与者，纵向从上到下是时间顺序。它想说明“谁先告诉谁做什么”，不是在画网页排版。

## 9. 会议结束、任务截止和任务完成，是三回事

会议有一个约定的时间；任务有一个要求完成的截止时间；完成状态表示执行人是否真的把事情做完。时间到了只能说明时间经过，不能证明工作完成。

任务正常进度是待开始、进行中、已完成。点击任务前的圆圈可以完成或重开，也可以通过状态选择操作。标记完成时记录实际完成时间，重开后清除完成时间。

未完成任务过了截止应理解为逾期。**逾期是时间与状态算出的提醒，不是完成，也不是自动取消。** 比如“整理展示反馈”截止在晚上8点，8点以后没人操作，就仍是没完成的任务。

取消表示这件事不再要求执行，与完成不同。当前规则由负责人取消或恢复，已完成任务要先重开再取消；恢复回待开始。执行人可以正常更新进度，但不能随意更换任务指派或自行取消任务。

会议页和“我的任务”读的是同一批任务记录，只是筛选不同：会议页看这场会关联的任务，个人页面看分配给自己的任务。不是把任务复制两遍，所以在一个地方完成，另一个地方重新读取后也会显示最新结果。

## 10. 删除、取消、归档，为什么要分开？

| 操作 | 现实含义 | 当前处理方式 |
| --- | --- | --- |
| 取消排期 | 这次时间征询不再继续 | 收集中先停止，避免还在收答案时直接删除 |
| 删除排期 | 这条无效记录不想放在正常列表 | 符合条件的记录进入回收站，保留底层数据 |
| 归档排期 | 已经办过，移入历史 | 已确认排期整理到历史，会议与任务继续可访问 |

删除采用“软删除”：设置一个删除标记，而不是立刻擦掉时段和答案。这样可以恢复，也避免误操作直接损坏历史关系。恢复会保留原业务状态，不会重新开始收集。

负责人可以删除草稿、没有会议的已关闭排期、已取消排期；已确认排期走归档。过时不等于可以无条件删除，要看它是否已经关联会议和任务。

这也解释了为什么“归档了会议相关排期”不能让未完成任务消失：整理历史并不等于事情已经完成。

## 11. 前端、后端、数据库，分别在忙什么？

可以借用餐厅的分工来理解，但它们实际都是这台电脑上运行的软件。

| 名称 | 类比 | 在MeetFlow里负责什么 |
| --- | --- | --- |
| 前端 | 菜单与点单界面 | 页面、输入框、矩阵、按钮、操作反馈 |
| 后端 | 接单和核对规则的工作人员 | 身份权限、输入检查、推荐、确认会议、任务修改 |
| 数据库 | 保存订单的账本 | 持久保存用户、小组、答案、会议和任务 |
| 接口（API） | 双方约定的点单格式 | 前端按约定发请求，后端按约定返回结果 |

例如点击“保存我的时间”：前端收集你的三态选择，按约定格式发送给后端；后端检查登录、参与资格和排期是否允许填写；通过后写入数据库；提交成功再返回结果；前端据此更新页面。

前端先检查输入，是为了及时提醒。后端还要重新检查，是因为页面检查可以被绕过，也可能已经过时。数据库保存后，刷新页面重新读取，答案才能回来；只改网页上的字，没有保存，就不算真正完成。

本项目用Vue和TypeScript做前端，FastAPI做后端，SQLAlchemy帮助程序读写SQLite。SQLite把数据库保存在文件里，适合目前的小组规模与本地单实例展示。技术名词分别对应上述分工，记住“各管什么”比背名字更有用。

登录后的会话可以理解为一张有时效的通行凭证。浏览器带着凭证请求数据，后端核对身份；退出后服务端撤销该会话。密码保存的是用于校验的哈希结果，不是把明文密码直接写进账本；哈希不能讲成“需要时解密回密码”。

## 12. 为什么本地网址别人打不开？上传GitHub不就上线了吗？

`localhost`和`127.0.0.1`都指访问者自己的电脑。你打开`http://localhost:8002`是在找你电脑上8002端口的服务；别人打开同一个地址，找的是他自己的电脑。

GitHub、Gitee保存的是代码和文档，不会因为上传了后端代码，就自动启动这套应用、提供数据库和公网服务。

公开部署需要让一台别人能访问的服务器持续运行程序，并处理域名或平台地址、HTTPS、配置、数据持久保存等问题。当前以本地展示为准，之前的公网尝试尚未验收成功，不能在汇报时说“同学已经都能直接在线用了”。

展示入口是本机的`http://localhost:8002/login`。独立演示库使用虚构账号与预置数据，方便演练，也避免把真实使用数据当作样例随意改动。虚构的四位使用者与实际两位项目组员不是一回事。

## 13. 如何说明“做出来了”，又不把结果说过头？

“能运行”“规则正确”“别人容易用”“确实帮助了小组”，是逐步增加的证据要求。

| 证据 | 能说明什么 | 不能单独说明什么 |
| --- | --- | --- |
| 自动化测试 | 检查过的输入、状态和异常符合预期 | 所有情况绝对没有问题 |
| 浏览器完整流程 | 页面和接口能够连起来操作 | 所有真实用户都容易上手 |
| 多个独立会话演示 | 不同账号能按权限协作 | 已经完成多人真人试用 |
| 真人试用与反馈 | 用户遇到了哪些问题、是否容易理解 | 未经测量的效率提升百分比 |

PPT引用2026年10月31日的最近完整回归记录：后端679项、前端313项。它们是测试项数量，不是用户人数，也不是功能数量；本次新增文稿测试也不能与产品回归混为一谈。

目前五位非开发者真实试用、公开发布与真实邮件仍待验收。可以说“本地核心流程已有验证记录”，不要说“课程全部验收已完成”或“已经证明提升了多少效率”。

## 14. 老师可能追问什么？

**为什么选这个题目？** 课程小组确实需要协调时间和跟进讨论结果。我们把一个完整、小而明确的场景做通，便于定义需求、实现和验证。

**与问卷有什么区别？** 问卷能收集答案。这里进一步区分必到成员、解释推荐风险，并把确定的会议接到纪要和任务；不宣称其他产品做不到这些。

**创新在哪里？** 在课程小组场景下，把关键成员优先、未知显式提示和会后跟进接起来。当前是规则与流程整合，不宣称发明了全新排期算法。

**为什么不能只按有空人数排序？** 人数可能一样，但必到成员没空和普通成员勉强，对能否开会的影响不同。PPT的A、B、C例子正是为了讲清这个差异。

**为什么不让系统自动确认第一名？** 第一名仍可能有冲突或未填。系统负责计算和提示，负责人根据实际情况作决定并记录风险理由。

**为什么要测试重复点击？** 浏览器可能没收到第一次成功回复，用户会再点。没有去重，可能产生多场会议或多项相同任务。

**为什么选SQLite，今后能不能扩大？** 它满足当前本地单实例和小规模协作，运行准备相对简单。扩展到更多并发用户时，需要重新评估部署、数据库和运行保障，不能只凭当前演示断言已经支持大规模使用。

**如何证明好用？** 还需要让非开发者无指导完成指定流程，记录耗时和卡点。自动化验证已经做了相当一部分，但真人易用性和实际收益还需要补证据。

## 15. 读完后，尝试不看文档回答

1. 排期和会议有什么区别？为什么任务要关联会议？
2. 未填为什么不能算有空？三态中为什么还要保留勉强？
3. 推荐第一步比较什么？示意例子里B为什么优于C和A？
4. 浏览器重复提交确认，为什么不会生成两场会议？
5. 任务截止后为什么仍可能没完成？取消和完成区别是什么？
6. 为什么页面隐藏按钮后，后端还要检查权限？
7. 给别人发localhost网址或GitHub仓库地址，为什么不等于公开运行了应用？
8. 我们已经有哪些证据，还有哪些结论不能声称完成？

能用自己的话讲清这些问题，就基本理解了项目的业务逻辑和技术分工。上台时不必照着全文背，按照“问题 → 规则 → 实现 → 演示 → 验证边界”的顺序讲即可。
