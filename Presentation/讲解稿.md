# MeetFlow 汇报讲解稿

展示：2026年11月6日。共9页，8分钟；其中第7页留2分30秒切换到本地 Demo。幻灯片备注中也附有逐页讲稿。

## 1. 从约时间，到会后行动（0:00—0:20）

大家好，我们的项目是 MeetFlow，也叫凑时，面向课程小组的排期和会议任务管理。它不只帮助大家选一个时间，还把会议确认、纪要和会后任务接在一起。下面先说明需求和设计，再用实际页面演示一遍。

## 2. 我们要解决的，是小组协作中的三处断点（0:20—1:20）

我们从三个典型场景出发：群聊里空闲时间分散，选时间时容易忽略关键成员，开完会后任务又散在聊天记录里。按照课程的 NABCD 分析，需求是集中协调并跟进结果；方案是三态填写、区分必到成员、给出推荐理由，再连接纪要和任务。预期收益是少做人工汇总，让每项决定有依据、有后续负责人。替代方式包括群聊、问卷和共享日历，我们聚焦的是临时课程小组的一次会议，而不是替代所有协作工具。推广先从本组和其他课程小组试用开始。这里的需求来自材料和场景分析，还没有把真实访谈或效率提升写成已完成的结论。

## 3. 两个角色，一条从排期到任务的流程（1:20—2:05）

参照需求获取课件，我们先明确参与者和交互。负责人建组、发起排期并确认会议，参与成员填写自己的时间；负责人编辑纪要、分配任务，执行人更新任务状态。范围控制在每组二十人、每次一到十五个候选时段。发布后冻结候选和参与者，避免旧答案失去含义。界面上隐藏按钮还不够，后端也会校验身份、组内关系和操作权限。我们用这些可观察的行为来写需求和验收，而不是只列页面名称。

## 4. 推荐先看必到冲突，再比较得分（2:05—3:00）

这是按当前规则计算的一组示意数据，不是真人调查。A、B、C 三个时段都有三人有空，但 A 中有必到成员没空，C 中有必到成员没有填写，不能只按人数看起来差不多就直接确认。我们的排序先比较必到冲突数，再比较得分、有空人数和时间，最后用固定标识保证同样输入得到同样顺序。计分时必到成员权重更高，没空和未填也有不同处理。结果中不仅显示名次，还明确提示谁冲突、谁未填。这里 B 最优；即使某次所有候选都冲突，系统仍会提示风险，不把第一名说成全员可参加。

## 5. 把业务流程落实为接口与数据关系（3:00—3:40）

需求分析与设计课件强调，要把文字描述转换成对象协作。我们的前端使用 Vue 和 TypeScript，负责表单、时间矩阵和任务交互；后端使用 FastAPI 处理权限和业务规则，通过 SQLAlchemy 访问 SQLite。本地同源、单实例运行，便于离线演示。数据上，小组包含排期，排期确认后最多生成一场会议，会议下面再关联纪要和任务。这条关系让会后任务能追溯到原来的会议和排期。

## 6. 一次确认，落成一场可追踪的会议（3:40—4:20）

以确认会议为例，我们用一个简化顺序图说明实现。浏览器提交候选时间后，后端不是直接插入记录，而是先获取写锁，重新核对排期状态、候选和负责人权限，再在同一事务里写入会议并更新排期。数据库还有唯一约束。同一个候选重复确认会返回已有会议，不会多建一场；状态已经变化或越权的请求会被拒绝。这样既把需求落实成了设计，也能为重复点击和并发情况编写测试。

## 7. 现场演示：选时间，再完成一项会后任务（4:20—6:50）

现在切到本地 Demo，使用虚构账号演示，不涉及真实个人日程。先看关键成员未填的结果，说明未填不等于有空。然后打开“从这里开始：四人空闲填写”，对三个时段依次选择勉强、有空、没空并保存。其他三位虚构成员已经填写，第二个时段会形成共同有空。负责人结束收集并确认推荐时段，进入会议，补充一句纪要。再创建一项由自己负责的“整理展示反馈”任务，截止选在十一月九日以后，去“我的任务”手动勾选完成，并在已完成分类中核对。重点是完成来自明确操作，而不是会议或截止时间过去就自动算完成。操作结束后回到第八页。若已经练过这个排期，就直接使用已有会议演示任务，或者新建一个草稿，不清空旧库。

## 8. 已验证的是功能链，真实使用效果仍待验证（6:50—7:35）

验证分成两部分。已有记录中，十月三十一日的后端完整回归通过六百七十九项，前端通过三百一十三项；另外有四个独立浏览器会话串联完整流程的记录，以及权限、失败恢复和备份重启检查。这些说明已有功能能够按规则运行，但不能代替真实用户反馈。公开发布还没有验收，真实邮件也未验证，五位非开发者试用仍待人工执行。因此我们没有给出节省百分之多少时间、满意度多少等缺乏依据的数字。

## 9. 下一步，用真实小组检验收益（7:35—8:00）

分工安排上，马若曦负责主要实现、集成和演示，陈明强参与文档复核与汇报协作，实际贡献按最终工作记录核对。项目按课程要求拆分了三十六项任务，并使用 Git、Gitee 和 GitHub 留存代码与文档。当前最重要的后续工作是真实小组试用和可持续的公网发布。我们希望验证的，不只是能否约上一次会，还包括会议决定能否持续落实。谢谢老师和同学。

## 演示前与故障备用

1. 在项目根目录启动独立展示环境：在终端运行 Src/backend/.venv/Scripts/python.exe Src/scripts/run_showcase.py。打开 http://localhost:8002/login 并预先登录。localhost 地址只用于这台电脑。
2. 先检查“从这里开始：四人空闲填写”是否仍在收集中。若已练习并确认，不清空旧库：准备新排期，或直接从已有会议讲任务闭环。新会议网址以实际跳转为准，不假定固定编号。
3. PPT第7页有本地链接；也可提前开好浏览器，Alt+Tab切换。网页备份可离线打开，方向键翻页、Home/End到首尾、全屏按钮进入全屏。
4. 页面失效时只刷新一次；超过10秒就回第7页，用真实截图讲同一流程，再继续第8页。PDF可作为字体或投影异常时的备用。
5. 不在展示前升级依赖或删除展示数据；真实试用仍标为待人工执行。
