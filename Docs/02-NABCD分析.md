# MeetFlow NABCD 分析

整理基线：B1｜2026-10-25。功能编号沿用[需求分析文档 V1.2](09-需求分析文档.md)，第一版范围见[需求边界](03-需求边界与MVP.md)。

## N：Need（需求）

课程小组经常需要集中讨论，但空闲时间、最终安排和会后任务容易分散在群聊中。本项目关注三个问题：成员时间难以汇总；简单按票数选择可能忽略必到成员；会议决定缺少明确负责人和后续状态。

目标用户为课程小组负责人和普通成员。社团、竞赛团队可复用同一流程，不增加专属业务。上述问题来自立项材料和场景分析，尚无用户访谈或试用数据证明其普遍程度。

## A：Approach（做法）

提供“建组—发起排期—填写三态—解释推荐—确认会议—记录纪要—跟踪任务”的连续流程。

- 成员通过邀请码入组，只填写本次候选时间，不读取私人日历。
- 区分必到成员和普通成员，展示时间矩阵、提交进度、推荐排名与理由。
- 必到成员未填写时提示未知；全部时间存在冲突时说明事实，由负责人决定。
- 负责人确认会议、编辑纯文本纪要并创建任务；成员查看自己的待办和小组任务列表。
- 第一版采用简单表单和列表，不实现拖拽看板、统计图、提醒推送或自动总结。

具体排序、权限和状态规则统一由[需求基线](09-需求分析文档.md)定义，本文不另设一套公式。

## B：Benefit（预期收益）

| 用户 | 预期收益 | 后续验证方式 |
| --- | --- | --- |
| 负责人 | 减少逐个询问和人工汇总，理解关键成员冲突 | 记录一次真实排期的耗时与重复询问轮次 |
| 成员 | 集中填写时间、找到最终安排和本人任务 | 观察填写、找会议、更新任务的完成情况 |
| 小组 | 会议结论能关联负责人、截止日期与状态 | 检查会后任务信息完整性及再次使用意愿 |

这些是待验证的收益，不填入未经测量的效率提升比例。文档检查、算法示例复算与真实用户试用分别记录。

## C：Competitors（竞争与替代方案）

| 替代方式 | 适合的情况 | MeetFlow 需要证明的价值 |
| --- | --- | --- |
| 群聊人工协调 | 人少、候选时间少，沟通成本低 | 结构化填写是否确实减少汇总工作 |
| 简单投票或问卷 | 快速收集选项 | 必到冲突和未知状态的解释是否有帮助 |
| 排期产品 | 直接协调多人时间 | 针对课程小组的纪要和任务衔接是否有价值 |
| 日历与综合协作工具 | 已长期使用同一平台的团队 | 独立工具带来的收益能否抵消迁移成本 |

多人排期和三态选择并非本项目独有。Doodle 官方说明已支持三种回答，且参与者无需注册账号；MeetFlow 的注册和入组过程反而需要验证是否增加负担。[Doodle 参与说明](https://help.doodle.com/en/articles/9457279-how-do-i-participate-in-a-group-poll)（核对日期：2026-10-25）。

差异定位是“关键成员约束可解释、排期与会后任务连续管理”，不主张所有同类工具都缺少这些功能。

## D：Delivery（交付与推广）

先完成第一版本地四账号演示和验收，再组织真实使用反馈。课堂公开发布属于后续课程交付阶段，需要在开放访问前补齐部署与安全验证，不能用本地运行代替课程发布成果。

试用记录包括测试者背景、操作任务、困难、原始意见、是否采纳及修改结果。初期以本组和熟悉的课程小组为对象，验证成功后再扩大使用范围。现阶段不填写尚未发生的访谈或推广效果。
