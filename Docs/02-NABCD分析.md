# MeetFlow NABCD分析

## 1. 项目定位

MeetFlow（凑时）面向课程项目小组，提供协作排期、会议确认、纪要记录和任务跟踪。首版聚焦临时学生团队的一次会议协作，以轻量级Web应用降低组织和参与成本。

## 2. N：Need（需求）

课程小组在约定讨论时间时，需要收集多名成员的空闲情况，并判断哪些成员必须参加。会议确定后，还需要明确讨论结论、任务负责人及截止时间。本项目从以下问题出发开展需求分析：

| 用户 | 待解决问题 | 对应需求 |
| --- | --- | --- |
| 小组负责人 | 群聊答案分散，候选时间需要反复汇总 | 集中收集三态答案，展示成员—时间矩阵 |
| 小组负责人 | 票数最多的时段可能与关键成员冲突 | 区分必到者，显示冲突及推荐依据 |
| 普通成员 | 难以快速找到最终安排和本人任务 | 统一显示会议详情与个人待办 |
| 整个小组 | 会议纪要和后续任务分散，进展难追踪 | 将会议决定关联到负责人、截止时间和状态 |

这些问题来自立项分析和典型场景推演，尚未形成访谈统计。后续重点核查实际发生频率、现有工具是否已足够，以及成员是否愿意额外填写候选时间。

## 3. A：Approach（做法）

核心流程为：创建小组 → 邀请加入 → 设置候选时段及必到成员 → 填写有空/勉强/没空 → 比较推荐与冲突 → 确认会议 → 记录纪要 → 分配和跟踪任务。

首版采取以下做法：

1. 通过注册账号和邀请码组织小组，不依赖校园身份接口或私人日历授权。
2. 以三态填写表达参与意愿，未填写单独显示为未知。
3. 用确定性规则优先比较必到成员冲突，再比较分数和其他排序条件。
4. 展示时间矩阵、人数统计和推荐理由，由负责人选择最终时间。
5. 在会议下记录议程、纪要和任务，保持小组任务与个人待办一致。

首版仅设置负责人和普通成员两类小组角色。基本矩阵和任务列表属于核心范围；热力图、复杂统计、额外管理员角色、站内提醒和导出分阶段扩展。

## 4. B：Benefit（收益）

| 对象 | 预期收益 | 评估方式 |
| --- | --- | --- |
| 负责人 | 减少重复汇总，快速定位必到者冲突 | 比较完成排期的耗时与重复询问次数 |
| 成员 | 快速表达状态，理解最终安排 | 观察填写时间、失败步骤及推荐解释理解情况 |
| 执行人 | 集中查看本人任务及截止时间 | 检查个人待办与会议任务一致性 |
| 团队 | 保存讨论决定，明确责任和进展 | 检查纪要、任务负责人、截止时间及状态完整性 |

收益目前为预期效果。原型与业务实现完成后，计划邀请5名非开发测试者验证入组和填写流程，并邀请真实课程小组试用；不预设已经实现的效率提升比例。

## 5. C：Competitors（竞争与替代方案）

| 替代方式 | 优点 | 采用该方式时需要考虑的问题 | MeetFlow的侧重点 |
| --- | --- | --- | --- |
| 群聊人工协调 | 无需学习新工具，适合少量成员 | 候选时间增多后如何汇总和保留结论 | 结构化收集、集中展示 |
| 简单投票或问卷 | 易于发起和收集偏好 | 仅按票数时如何体现必到成员 | 冲突优先、三态统计、公开排序依据 |
| 日历式协调 | 适合已有共享日程习惯的团队 | 临时成员如何组织共享与参与 | 围绕本次候选时间填写，无需私人日历授权 |
| 综合协作平台 | 长期协作功能丰富 | 如何将排期收集、确认与任务分配串联 | 围绕一次会议组织连续流程 |

比较针对使用方式，不将同类产品概括为统一缺少某项能力。MeetFlow的差异化假设是：临时课程小组需要较少配置、可解释的排期以及紧接会议的任务跟踪。对已能用现有工具顺利协作的团队，迁移价值可能有限。

## 6. D：Delivery（推广与交付）

第一阶段完成四账号、三时段、两任务的端到端验收，验证核心流程。第二阶段邀请其他课程小组进行真实排期，提供演示入口和邀请码，记录候选设置、三态理解、推荐解释及任务查找方面的问题。第三阶段根据反馈修改一次版本，再通过班级或社团交流渠道介绍项目。

试用记录包括小组规模、完成排期数量、填写困难、选择理由、任务信息完整性和再次使用意愿。推广以实际使用和反馈为依据，不以单纯访问量代替价值验证。

## 7. 对需求范围的影响

需求优先级由核心价值确定：账户与小组、候选时间、三态填写、必到冲突、推荐解释、会议确认、纪要及任务跟踪为P0；额外角色、热力图和统计增强为P1；提醒、导出等为P2。首版不包含音视频、即时聊天、付费服务、私人日历读取或AI自动纪要。
