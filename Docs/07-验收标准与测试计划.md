# MeetFlow 验收标准与测试计划

## 1. 文档目的

本文档用于定义“功能做到什么程度才算完成”，并提前为课程要求的功能测试、测试用例和测试报告准备结构。任何功能在未满足验收标准、未通过相关测试前，不应标记为完成。

## 2. MVP 端到端验收场景

### 场景 E2E-01：完整排期与会议闭环

1. 用户A注册、登录并创建小组；
2. 用户B、C、D通过邀请码加入；
3. A创建包含三个候选时间段的排期；
4. A将B设置为必到成员；
5. A、B、C、D分别填写不同的空闲状态；
6. 系统显示完整时间矩阵，并将必到成员没空的时间排在较后位置；
7. 系统对推荐第一名给出可理解的理由；
8. A确认其中一个时间，系统生成会议；
9. A填写会议纪要，并为C、D创建任务；
10. C和D分别更新任务状态；
11. 小组任务看板和个人待办均显示正确结果。

以上步骤全部可重复完成且无严重错误，才视为 MVP 主流程通过。

## 3. 功能验收标准

| 编号 | 功能 | 验收标准 |
| --- | --- | --- |
| AC-01 | 注册 | 合法信息注册成功；重复用户名/邮箱、弱密码和格式错误得到明确提示 |
| AC-02 | 登录 | 正确密码可登录，错误密码不能登录，受保护页面未登录不可访问 |
| AC-03 | 创建/加入小组 | 创建者成为负责人；有效邀请码可加入；无效或停用邀请码被拒绝 |
| AC-04 | 成员权限 | 普通成员不能管理成员、确认会议或修改他人投票 |
| AC-05 | 候选时间 | 结束时间不晚于开始时间、重复时间段等非法输入被拒绝 |
| AC-06 | 填写状态 | 用户可以保存并在截止前修改本人答案；不能修改他人答案 |
| AC-07 | 截止控制 | 截止后普通成员不能继续提交；负责人关闭后状态正确更新 |
| AC-08 | 推荐排序 | 必到成员冲突数优先；同一输入始终得到同一排序 |
| AC-09 | 推荐解释 | 页面显示必到冲突、有空、勉强、没空、未提交和推荐原因 |
| AC-10 | 确认会议 | 只有有权限者可确认，且只能选择所属排期的有效时间段 |
| AC-11 | 会议纪要 | 有权限者可编辑，普通无权限用户不能编辑 |
| AC-12 | 任务管理 | 创建、指派、状态更新、截止日期和个人待办保持一致 |
| AC-13 | 数据隔离 | 一个小组的成员不能访问另一个未加入小组的数据 |
| AC-14 | 错误反馈 | 网络错误、空数据、无权限和校验失败均有可理解提示 |

## 4. 单元测试重点

### 4.1 推荐算法

- 所有成员有空；
- 普通成员票数多但必到成员没空；
- 多个时间段总分相同；
- 部分成员未提交；
- 全部时间均存在必到成员冲突；
- 只有一名参与者；
- 候选时间为空时正确报错；
- 输入顺序变化不改变最终排序规则；
- 推荐解释中的人数与计算结果一致。

### 4.2 状态转换

允许的排期转换：

```text
DRAFT → OPEN → CLOSED → CONFIRMED
   └────→ CANCELLED
OPEN ───→ CANCELLED
CLOSED ─→ CANCELLED
```

应测试允许转换和非法转换，例如已确认排期不能重新开启。

### 4.3 权限函数

- 非成员拒绝访问；
- 普通成员只修改本人数据；
- 管理员能够创建排期但不能转让负责人；
- 负责人能够管理成员；
- 系统管理员权限不应自动等同于小组成员业务权限，除非维护接口明确允许。

## 5. 后端集成测试

| 模块 | 关键测试 |
| --- | --- |
| 认证 | 注册、登录、令牌失效、未认证访问 |
| 小组 | 创建、加入、重复加入、邀请码停用、移除成员 |
| 排期 | 草稿创建、开启、截止、取消、非法时间段 |
| 投票 | 保存、覆盖本人答案、截止后拒绝、跨小组拒绝 |
| 推荐 | 返回排序、统计和解释，数据变化后结果同步更新 |
| 会议 | 确认时间、重复确认、非法时间段、会议详情 |
| 任务 | 创建、指派、状态更新、个人待办、权限隔离 |

测试数据库必须与开发数据隔离，并在每个测试后清理或回滚。

## 6. 前端测试与人工测试

自动化测试至少覆盖：

- 登录状态和路由守卫；
- API错误信息展示；
- 时间状态组件的三态切换；
- 推荐结果排序展示；
- 任务状态更新；
- 权限不同导致的按钮显示差异。

人工测试至少覆盖：

- 桌面浏览器完整主流程；
- 手机宽度下填写排期；
- 加载、空数据、错误、无权限状态；
- 快速连续点击不会创建重复数据；
- 日期时间和时区显示正确；
- 长标题、长姓名和较多成员时页面不严重错位。

## 7. 性能与可靠性测试

课程项目不预设夸张的性能数字，应记录真实测试环境和结果。建议测试：

- 50名成员、30个候选时间段时的推荐计算时间；
- 1000条任务数据时的分页查询；
- 多个用户连续提交空闲状态时的数据一致性；
- 重复请求确认会议时是否生成重复会议；
- 后端重启后数据是否保持；
- 前端遇到接口超时或失败时是否能够恢复操作。

## 8. 用户反馈计划

建议邀请 5 至 10 名非开发成员完成一个真实排期，记录：

1. 加入小组和填写排期所需时间；
2. 是否理解三种空闲状态；
3. 是否理解推荐理由；
4. 是否能独立找到最终会议时间；
5. 是否能创建或更新任务；
6. 最困惑的页面或操作；
7. 最希望增加或删除的功能；
8. 是否愿意在下一次小组讨论中继续使用。

用户反馈报告应包含：测试者背景、任务、原始意见摘要、问题归类、修改决定、修改前后截图和未采纳意见理由。

## 9. 完成定义（Definition of Done）

一个任务只有同时满足以下条件才算完成：

- 功能符合需求编号和验收标准；
- 权限和非法输入得到处理；
- 自动化测试已经添加并实际通过；
- 页面包含加载、空数据和错误状态；
- 接口或数据库变更已经同步更新文档与迁移；
- 不包含调试输出、硬编码密码或未使用代码；
- 由至少一名非实现者完成代码或功能复核；
- 相关修改已经以清晰的提交信息提交到 Gitee。
