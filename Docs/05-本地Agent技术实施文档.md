# MeetFlow 本地 Agent 技术实施文档

> 本文档是本地 Agent 的开发总纲，不是第一次课必须提交的材料。Agent 在修改代码前必须阅读本文档以及 `03-需求边界与MVP.md`、`06-数据库API与页面设计.md`、`07-验收标准与测试计划.md`。

## 1. 开发目标

实现一个可以本地稳定运行的前后端分离 Web 应用，完整支持：

```text
用户与小组 → 排期创建 → 成员填写 → 推荐解释 → 会议确认
→ 会议纪要 → 任务分配 → 状态跟踪
```

开发优先级依次为：正确性、完整性、可测试性、易用性、视觉效果。不得为了扩展功能破坏 MVP。

## 2. 固定技术栈

### 2.1 前端

- Vue 3；
- TypeScript，开启严格模式；
- Vite；
- Vue Router；
- Pinia；
- Axios；
- Element Plus；
- ECharts；
- Vitest。

### 2.2 后端

- Python 3.12；
- FastAPI；
- SQLAlchemy 2.x；
- Alembic；
- Pydantic 2.x；
- SQLite 作为默认开发数据库；
- Pytest；
- 密码哈希使用可靠库，不自行实现加密算法；
- JWT 或安全的服务端会话用于身份认证。

如本地环境不支持某个具体小版本，可以在不改变架构的前提下使用相邻稳定版本，并在 README 记录实际版本。

## 4. 系统架构

```text
浏览器
  ↓ HTTPS/HTTP + JSON
Vue 3 单页应用
  ↓ REST API
FastAPI 路由层
  ↓
服务层：权限、排期、推荐、会议、任务
  ↓
数据访问层 / SQLAlchemy
  ↓
SQLite（开发）或 PostgreSQL（部署）
```

## 7. 排期推荐规则

### 7.1 输入

- 候选时间段；
- 参与成员；
- 成员是否必到；
- 每名成员对每个时间段的状态：`AVAILABLE`、`MAYBE`、`UNAVAILABLE`；
- 是否已经提交。

### 7.2 默认权重

- 必到成员权重：3；
- 普通成员权重：1；
- 有空状态值：2；
- 勉强状态值：1；
- 没空状态值：-2；
- 每名必到成员没空额外扣 20 分；
- 每名未提交成员额外扣 2 分，仅用于提醒不确定性。

```text
基础分 = Σ(成员权重 × 状态值)
最终分 = 基础分 - 20 × 必到成员没空数 - 2 × 未提交成员数
```

排序依次比较：

1. 必到成员没空数更少；
2. 最终分更高；
3. 有空成员总数更多；
4. 时间开始更早。

推荐解释至少包含：必到成员冲突数、有空人数、勉强人数、没空人数、未提交人数和排序原因。

所有权重定义为集中配置或常量，禁止散落在接口代码中。

## 8. 权限原则

- 所有小组数据接口先验证用户是否属于该小组；
- 创建者默认为负责人；
- 只有负责人能够更新邀请码、管理成员、开启/关闭排期和确认会议；
- 成员只能修改自己的空闲状态；
- 任务负责人可以更新本人任务状态；
- 会议记录人和小组负责人可以编辑纪要；
- 后端必须实施权限校验，不能只依赖前端隐藏按钮。

## 9. 数据一致性原则

- 用户名和邮箱唯一；
- 邀请码唯一且可以失效；
- 同一用户在同一小组只能有一个有效成员关系；
- 同一排期中的候选时间段不得完全重复；
- 同一用户对同一时间段只能有一条投票记录；
- 只有收集中且未截止的排期允许普通成员修改答案；
- 确认会议必须引用该排期的有效候选时间段；
- 唯一负责人退出小组前必须转让权限；
- 删除采用明确策略：优先软删除关键业务数据，避免无意丢失历史记录。

## 10. 代码质量要求

- 所有公开接口使用明确的请求和响应模型；
- 统一错误响应结构；
- 时间统一以 UTC 存储，前端按本地时区展示；
- 禁止在代码中提交密钥、密码和生产配置；
- 提供 `.env.example`；
- 数据库结构使用迁移管理；
- 推荐算法、状态转换和权限判断必须有单元测试；
- 关键接口必须有集成测试；
- 前端至少测试关键状态转换和数据展示函数；
- 删除无用示例代码、调试输出和未使用依赖；
- README 必须包含安装、迁移、启动、测试和演示账号说明。

## 11. Agent 工作规则

1. 开始每个阶段前，先检查当前仓库状态和已有实现；
2. 只实现当前阶段范围，不提前扩展；
3. 修改数据库模型时同步生成迁移；
4. 修改接口时同步更新类型、测试和文档；
5. 每完成一个模块立即运行相关测试；
6. 不覆盖组员已有且与当前任务无关的修改；
7. 遇到需求歧义时优先遵循 `03-需求边界与MVP.md`；
8. 如果必须改变既定需求，先在变更记录中说明原因和影响；
9. 阶段结束时输出：修改文件、已完成功能、测试结果、遗留问题、下一步建议；
10. 不得声称未实际运行的测试已经通过。
