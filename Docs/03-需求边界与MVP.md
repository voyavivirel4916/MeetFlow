# MeetFlow 需求边界与 MVP

## 1. 文档目的

本文档用于确定 MeetFlow 第一版必须完成的范围，防止开发过程中持续增加功能。它是正式《需求规格说明书》的前置材料；如需求发生变化，应记录变更原因、影响范围和确认人。

## 2. 产品愿景

为课程小组和学生团队提供低门槛、可解释的多人排期工具，并将确定后的会议继续连接到纪要和任务跟踪，形成协作闭环。

## 3. 用户角色

| 角色 | 说明 | 主要目标 |
| --- | --- | --- |
| 游客 | 未登录用户 | 查看产品介绍，进入登录或注册页 |
| 普通用户 | 已注册用户 | 创建或加入小组，参与排期，查看会议和个人任务 |
| 小组负责人 | 创建小组或被授予管理权限的用户 | 管理成员、发起排期、指定关键成员、确认会议和分配任务 |
| 系统管理员 | 维护系统的课程项目成员 | 查看异常数据、禁用违规账号、维护系统基本运行 |

一个普通用户可以在不同小组中拥有不同角色。

## 4. 核心用户故事

- 作为小组负责人，我希望创建小组并通过邀请码邀请成员，以便快速建立协作空间；
- 作为小组负责人，我希望设置多个候选时间段，以便成员集中填写可用时间；
- 作为小组负责人，我希望指定必到成员，以便推荐结果优先避开关键成员冲突；
- 作为普通成员，我希望快速填写“有空、勉强、没空”，以便准确表达个人状态；
- 作为所有成员，我希望查看时间矩阵和推荐理由，以便理解最终选择；
- 作为小组负责人，我希望确认会议并发布议程，以便所有成员获得统一结论；
- 作为会议记录人，我希望记录纪要并创建任务，以便落实会议决定；
- 作为任务负责人，我希望查看个人待办并更新状态，以便团队了解进度。

## 5. MVP 功能需求

### 5.1 账户与身份

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-A01 | 用户可以使用用户名、邮箱和密码注册 | P0 |
| FR-A02 | 用户可以登录、退出并查看个人信息 | P0 |
| FR-A03 | 系统必须对密码进行安全哈希，不能保存明文密码 | P0 |
| FR-A04 | 用户只能操作自己有权限访问的小组数据 | P0 |

### 5.2 小组管理

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-G01 | 用户可以创建小组并成为负责人 | P0 |
| FR-G02 | 系统为小组生成可更新的邀请码 | P0 |
| FR-G03 | 用户可以使用邀请码加入小组 | P0 |
| FR-G04 | 负责人可以查看、移除成员和转让负责人 | P1 |
| FR-G05 | 成员可以主动退出小组，但唯一负责人退出前必须转让权限 | P1 |

### 5.3 排期管理

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-P01 | 负责人可以创建排期并填写主题、说明、地点和填写截止时间 | P0 |
| FR-P02 | 负责人可以添加、修改和删除多个候选时间段 | P0 |
| FR-P03 | 候选时间段开始时间必须早于结束时间，且不能重复 | P0 |
| FR-P04 | 负责人可以指定必到成员和普通成员 | P0 |
| FR-P05 | 排期具有草稿、收集中、已截止、已确认、已取消状态 | P0 |
| FR-P06 | 收集中且未到截止时间的排期允许成员填写或修改状态 | P0 |

### 5.4 空闲状态与推荐

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-V01 | 成员可以对每个候选时间填写有空、勉强或没空 | P0 |
| FR-V02 | 系统应记录最后提交时间，并允许截止前覆盖本人旧答案 | P0 |
| FR-V03 | 系统展示成员—时间段矩阵和汇总统计 | P0 |
| FR-R01 | 系统按照确定性规则计算推荐排名 | P0 |
| FR-R02 | 排名应优先减少必到成员无法参加的数量 | P0 |
| FR-R03 | 系统展示每个时间段的分数构成和冲突成员 | P0 |
| FR-R04 | 相同数据必须产生相同排序结果 | P0 |

### 5.5 会议与任务

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-M01 | 负责人可以从候选时间中确认最终会议时间 | P0 |
| FR-M02 | 确认后系统生成会议记录，并向组内成员展示 | P0 |
| FR-M03 | 负责人或记录人可以编辑会议议程和纪要 | P1 |
| FR-T01 | 有权限的成员可以从会议中创建任务 | P0 |
| FR-T02 | 任务包含标题、说明、负责人、截止时间和状态 | P0 |
| FR-T03 | 任务负责人可以更新待办、进行中、已完成状态 | P0 |
| FR-T04 | 用户可以查看个人待办和所在小组任务列表 | P0 |

### 5.6 统计与提醒

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-S01 | 首页展示用户待填写排期和临近截止任务 | P1 |
| FR-S02 | 小组页展示任务完成率和成员任务数量 | P1 |
| FR-S03 | 系统提供站内提醒并支持标记已读 | P2 |
| FR-S04 | 支持将排期结果导出为图片 | P2 |

## 6. 非功能需求

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-01 | 易用性 | 新用户在不阅读说明书的情况下，应能在 3 分钟内完成加入小组和填写排期 |
| NFR-02 | 可解释性 | 推荐结果必须展示必到成员冲突数、各状态人数和排序原因 |
| NFR-03 | 安全性 | 密码不得明文保存；所有受保护接口必须验证身份和小组权限 |
| NFR-04 | 数据一致性 | 同一用户对同一候选时间只保留一条有效状态 |
| NFR-05 | 性能 | 在课程项目预期数据规模下，普通列表与推荐接口应保持流畅，并在测试报告中记录实测结果 |
| NFR-06 | 可维护性 | 前后端分层清晰，核心推荐逻辑与接口层分离，关键函数具有测试 |
| NFR-07 | 可部署性 | 项目必须提供清晰的本地启动说明；部署失败时仍能本地完整演示 |
| NFR-08 | 兼容性 | 支持当前主流桌面浏览器，核心排期页面在手机宽度下可基本使用 |

## 7. 推荐算法边界

第一版只使用确定性规则，不使用机器学习或大模型：

- 必到成员没空是最高优先级冲突；
- 有空高于勉强，勉强高于没空；
- 未填写成员不默认为有空；
- 同分时依次比较必到成员冲突数、总可用人数、候选时间先后；
- 所有权重写入配置或常量并在文档中说明。

## 8. 第一版明确不实现

- 实时聊天和音视频会议；
- 微信、QQ、短信和邮件推送；
- 大模型自动生成会议总结；
- 读取用户私人日历；
- 对接学校教务系统；
- 地图导航和地点预约；
- 支付、广告和商业化；
- 原生 Android、iOS 或微信小程序；
- 复杂组织层级和企业审批流。

上述功能可以写入“未来工作”，但不得影响 MVP 按时完成。

## 9. 第一版成功标准

当四名测试用户能够完成以下完整流程时，MVP 达到基本成功标准：

1. 一名用户创建小组并邀请另外三人加入；
2. 负责人创建至少三个候选时间段并指定必到成员；
3. 所有成员分别填写空闲状态；
4. 系统生成稳定、可解释的推荐排名；
5. 负责人确认其中一个时间并生成会议；
6. 记录人填写会议纪要并创建至少两个任务；
7. 任务负责人更新状态；
8. 小组页正确显示任务进度，个人页正确显示待办。
